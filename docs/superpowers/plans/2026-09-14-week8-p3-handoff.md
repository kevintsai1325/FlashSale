## 一、最重要的三件事

### 1. P1 的「三副本比較慢」被推翻了，而且原因是量測方式

P1 量到三副本的 p95 比單副本慢 41%，當時的結論是「水平擴展只增加資源競爭」。
那個結論**是錯的**，錯在壓測腳本用的是封閉模型（`per-vu-iterations`）：負載總量由 VU 數決定，
與後端有幾個副本無關。副本再多也不會有更多請求進來，只會多幾個 JVM 搶同一台機器的 CPU。

改用開放模型（`ramping-arrival-rate`，到達率外生）重量之後：

| 到達率 | 1 副本 | 3 副本 | 5 副本 |
|---|---|---|---|
| 150 | 7.9 ms | 8.6 ms | 8.7 ms |
| 300 | 6.2 ms | 6.0 ms | 6.2 ms |
| **600** | **130.0 ms** | **6.9 ms** | **6.8 ms** |
| **900** | **打不進去** | **70.9 ms** | **61.0 ms** |

（accept 腳的 p95，數字出處 `docs/portfolio/data/k8s-saturation-results.json`）

**水平擴展在 600 rps 以下毫無價值，600 以上才開始決定生死。** 三副本在 600 rps 比單副本快
18.8 倍。而 3 → 5 只從 70.9 ms 改善到 61.0 ms —— 報酬遞減，因為瓶頸已經下移到資料庫。

P1 的原始結果檔沒有刪，但已加註「此結論已被 P3 以開放模型推翻」。

### 2. 瓶頸是 Postgres 連線池，而且有一道硬天花板

單副本在 900 rps 時，`hikariPending` 連續 15 個樣本、跨越 63.7 秒維持在 131–176 ——
執行緒在排隊等連線池（每副本上限 30 條）。

更關鍵的是掃描到 5 副本時直接撞牆：

```
5 副本 × HikariCP 30 = 150 > Postgres 預設 max_connections 100
psql: FATAL: sorry, too many clients already
```

**這道牆在 CPU 或吞吐量到頂之前就先出現。** 為了量完曲線，我把 `max_connections` 調到 300
（`k8s/base/data.yaml`，附完整理由註解），三組掃描全部在新設定下重跑以保持一致。

這是 P4／P5 拆分服務與資料庫最硬的理由：連線數是跟著副本數線性成長的，而資料庫的
連線上限是全域的。

### 3. HPA 會動，但在秒殺場景不如預先擴容

| | HPA（3 → 8） | 預先擴容到 8 |
|---|---|---|
| accept p95 | 2972.9 ms | **434.2 ms** |
| 失敗請求 | 963 | **0** |
| 掉的迭代 | 9522 | 100 |

HPA 的**決策**很快：負載開始後約 12 秒就做出擴容決定，約 43 秒新副本就緒。問題不在控制迴圈，
在於**五個 JVM 同時冷啟動**把單節點的 CPU 吃光，觸發 liveness probe 逾時，
連原本健康的 Pod 都被殺掉重啟 —— 自己打掛自己。

**兩次執行都沒有通過資料品質守門**（掉迭代太多），所以這組數字只能當「反應視窗內的受損程度」，
不能當吞吐量測。文件裡有寫明。

## 三、過程中的兩個事故

### 事故 1：兩支 k6 同時對同一叢集施壓

子代理在我接手掃描後仍持續重跑，一度有兩支 k6 並行 —— 而且其中一支自稱在量「單副本」，
當時叢集已被我縮放到三副本。**兩邊的數字都不可信，全部丟棄重跑。**

教訓：多個執行者共用一個叢集時，必須有單一的執行權責歸屬。後來改成「掃描一律由我執行」。

### 事故 2：我自己寫進文件的數字有兩次是推論而非量測

- 時鐘問題：我把成因寫成「牆鐘會往回跳」，實際上單調時鐘也快 4.5%
- 連線容量：我寫「NodePort 2000 條同時連線 0 失敗」，重測是 300 條就被拒 90 條

兩次都是「量到一個結果 → 推論出一個機制 → 把推論當量測寫下去」。
這也是為什麼 P3 的第一個任務是先做資料品質守門，而不是先做壓測腳本。

**而且這個毛病在 P3 內部又犯了一次**：最終審查發現 `reservationMaxMs` 在高負載讀到 0
被寫成「Redis 沒有變慢」—— 實際上那是指標停止回報（同一份文件在負載更低的情境反而寫 48.9 ms）。
已更正，而且真實資料（掉零是漸進的：150 rps 全報、300 rps 已有 27–39% 讀 0、600 以上全 0）
比原本的敘述更支持「指標失去回報能力」這個解讀。

## 四、還沒做的事

### 建議優先處理

1. **把資料品質守門擴充成能偵測「指標恆為 0」**（R17）。
   現在的守門會檢查延遲分位數單調、掉迭代、新連線數，但不會問「這個下游指標在 150 rps 有值、
   在 900 rps 卻整段為 0，是不是根本沒在回報」。這正是 P3 內部犯的那次錯誤，加上這條規則就能
   永久堵住。屬任務規模（新增驗證器 + 測試）。

2. **決定 Zipkin 怎麼辦**。壓測時重啟 24 次（512Mi 上限撐不住約 1500 req/s 的 span 量）。
   選項：調降取樣率、加記憶體、或換成有儲存後端的部署。

3. **HPA 的 `maxReplicas` 與資料庫連線上限是綁在一起的**。
   現在 `maxReplicas: 8` × 每副本 30 條 = 240，而 `max_connections` 是 300，真正的天花板是 10 副本。
   `hpa.yaml` 已加註解記錄這個算式，但**調高 `maxReplicas` 前一定要先調 `data.yaml`**。

4. **liveness probe 沒有設 `timeoutSeconds`**（吃預設的 1 秒），而 backend 的 `limits.cpu` 是 2。
   冷啟動風暴時 JVM 來不及在 1 秒內回應探針就被殺。若要讓 HPA 真的可用，這是第一個該調的東西。

### 已知但刻意不修（風險低）

- `analyze-saturation.mjs` 同時是純函式模組與 CLI 進入點
- `buildCurve` 若被直接餵未驗證資料，`p95` 為 undefined 時會靜默判定為未劣化
- `saturation.js` 覆蓋 k6 全域的 trend 統計，未來若加 p90 檢查會靜默讀到 0（與當初 p99 同一個陷阱）
- 契約測試沒有斷言 PDB 的 `selector`（selector 改壞會讓 PDB 靜默失效）
- 下游取樣的 JSONL 檔首有 BOM，逐行 parse 的讀取器會在第一行拋錯
- `.superpowers/` 被 gitignore，所以文件裡指向 task report 的引用在全新 clone 上是死連結
  （§4、§5 的數字已另外存成 `docs/portfolio/data/k8s-hpa-results.json`，不受影響）

## 六、怎麼重現這些量測

```powershell
# 一組掃描（一個副本數、四個到達率，約 12 分鐘）
./load-tests/k8s/run-saturation.ps1 -Replicas 3 -Rates '150,300,600,900' `
  -PreAllocatedVUs 300 -MaxVUs 1200 -AdminPassword '<自訂密碼>'

# 判讀（會擋掉不可信的資料，別去放寬它的門檻）
node load-tests/k8s/analyze-saturation.mjs <結果目錄>
```

注意事項都寫在 `load-tests/README.md`：`StartRate` 不可超過 200（Rancher Desktop 的中繼層
只容得下約 210 條同時建立中的連線）、施壓端必須在 Windows（VM 內時鐘快約 3.5%）、
量測邊界是 NodePort 直達 backend（不經 Nginx 與 TLS）。
